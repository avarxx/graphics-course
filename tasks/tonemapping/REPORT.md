# Тон-маппинг и цветокоррекция — решение

Основа — решение задания `skybox` (террейн, камни, отложенное освещение, декали, процедурное небо).

## Структура кадра

```
0. Sky bake          (только при изменении параметров неба)
1-3. Depth prepass, G-buffer, decals
4. Lighting          -> HDR-картинка B10G11R11_UFLOAT (линейная яркость, без экспозиции и кривой)
5. Lum min/max       compute: минимум и максимум log2 яркости
6. Histogram         compute: гистограмма log2 яркости, 100 корзин между min и max
7. Exposure          compute: экспозиция по гистограмме + адаптация во времени
8. Post-process      полноэкранный треугольник: экспозиция -> кривая -> sRGB -> 3D LUT -> дизеринг -> backbuffer
9. ImGui
```

Код: `Tonemapper.{hpp,cpp}`, `ColorLut.{hpp,cpp}`, `shaders/TonemapParams.h`, `shaders/luminance*.glsl`,
`shaders/minmax*.{glsl,comp}`, `shaders/histogram*.{glsl,comp}`, `shaders/exposure.comp`,
`shaders/postprocess.frag`, папка `luts/`.

### Шаг 1. HDR-картинка и перенос в LDR

* `WorldRenderer::allocateResources` создаёт `hdrTarget` формата `B10G11R11_UFLOAT` (color attachment +
  sampled). В него рисуют проход освещения и форвардный эталон; небо тоже пишется туда в линейных
  единицах. ACES и экспозиция из шейдеров освещения убраны.
* `postprocess.frag` переносит HDR в backbuffer `B8G8R8A8_UNORM`. Если выключить тон-маппинг,
  цветокоррекцию и sRGB (`--no-tonemap --no-grading --no-srgb`), шейдер просто пишет значение
  как есть. **Кода для квантования не нужно**: запись в UNORM-аттачмент сама ограничивает значение
  отрезком [0, 1] и округляет его до одного из 256 уровней.

### Шаг 2. Экспозиция и тон-маппинг

**Что такое яркость.** У RGB нет «яркости» как отдельной компоненты: каналы глаз воспринимает
по-разному (зелёный кажется гораздо ярче синего). Яркость — это компонента Y цветового пространства
CIE XYZ: для основных цветов sRGB / Rec.709 `Y = 0.2126 R + 0.7152 G + 0.0722 B`, и формула
верна только для **линейных** значений (то есть на HDR-картинке до гаммы). В других моделях
яркость выделена явно: Y в XYZ / xyY, L* в CIELAB (перцептивная светлота), Y' в YCbCr (luma, но
считается по гамма-закодированным значениям, это уже не то же самое), V в HSV не перцептивна совсем.

**Почему логарифмы.** Освещённость в HDR-кадре различается на порядки (тень и облако на солнце —
несколько «стопов»), а глаз воспринимает отношения, а не разности (закон Вебера–Фехнера).
Равные корзины по log2 — равные перцептивные шаги. Если строить гистограмму по линейной яркости,
почти все тёмные пиксели попадут в первую корзину.

Проходы:

1. `minmax_*.comp` — min и max `log2(Y)`. Атомарные min/max есть только для целых, поэтому float
   отображается в uint с сохранением порядка (у положительных ставится знаковый бит, отрицательные
   инвертируются), `luminance.glsl`.
2. `histogram_*.comp` — 100 корзин, равномерно от минимума до максимума.
3. `exposure.comp` — выбор экспозиции (одна инвокация, 100 корзин — это ничто):
   * по умолчанию **усечённое среднее** log2 яркости между 40-м и 95-м перцентилями: самые тёмные
     (вода, глубокие тени) и самые яркие (солнце, блики) пиксели не влияют. Также можно выбрать
     медиану или обычное среднее. Медиана — частный случай (оба перцентиля 0.5);
   * средняя log2 яркость отображается в «ключевое» значение (серая карта 18 %, + компенсация
     экспозиции в EV): `exposure = key / 2^adapted`;
   * значение ограничено допустимым диапазоном, чтобы взгляд прямо на солнце не делал всё чёрным.
4. **Устойчивость к повороту камеры** (пункт 5): адаптация во времени в лог-пространстве
   `adapted += (target - adapted) · (1 - exp(-dt · speed))` — не зависит от частоты кадров,
   к свету глаз привыкает быстрее (3 1/с), чем к темноте (1.2 1/с); dt ограничен 0.1 с, чтобы
   долгий кадр (например, перезапекание неба) не давал скачка. Плюс усечённое среднее само по себе
   не реагирует на маленькие яркие объекты. Вся цепочка на GPU, CPU результат не ждёт.
5. `postprocess.frag` умножает цвет на экспозицию и применяет кривую: Clamp (наивный вариант),
   Reinhard по яркости с белой точкой, ACES (аппроксимация Narkowicz), Hable (Uncharted 2).
   По умолчанию ACES.

**Shared memory против глобальных атомиков.** Оба прохода по картинке есть в двух вариантах
(`*_shared.comp` / `*_global.comp`, общий код в `.glsl` с `#define`), переключаются в ImGui или
`--global-atomics`:

* min/max: в shared-варианте — редукция деревом в shared memory по группе 16×16, затем одна пара
  глобальных атомиков на группу (3600 вместо 921 600 на 1280×720);
* гистограмма: в shared-варианте группа накапливает локальную гистограмму атомиками в shared memory
  и добавляет в глобальную только непустые корзины. В глобальном варианте — атомик на пиксель, и
  соседние пиксели почти всегда попадают в одну и ту же корзину, то есть бьют в один адрес.

Замер на программном Vulkan (lavapipe, 2 ядра CPU, 1280×720, 200 кадров, два прогона каждого
варианта): кадр целиком 337 / 321 мс с shared memory против 353 / 354 мс с глобальными атомиками,
то есть глобальный вариант дороже примерно на **25 мс**. Таймстампы lavapipe внутри compute-проходов
показывают ~0.1 мс и недостоверны (это растеризатор на CPU), поэтому сравнивалось полное время
кадра, где отличается только этот вариант. В обоих вариантах в гистограмме ровно 921 600 пикселей
(видно в ImGui и в `--print-timings`).

**Нужно ли менять auto-gamma в Etna?** Нет, `autoGamma = true` (по умолчанию) оставлен намеренно.
Etna при этом выбирает swapchain `B8G8R8A8_UNORM` — значения пишутся в него как есть, и монитор
интерпретирует их как sRGB-закодированные. Поэтому шейдер сам применяет точную кусочную функцию
sRGB (не `pow(1/2.2)`). Это нужно и для шага 1 («просто квантующий» UNORM-бэкбуфер), и для шага 3:
LUT берёт на вход цвет **после** гаммы. С `autoGamma = false` swapchain стал бы `_SRGB`, железо
кодировало бы сами, и выход LUT пришлось бы декодировать обратно в линейный — лишняя пара
преобразований с потерей точности в 8 битах. (Название флага в Etna сбивает с толку: «auto» в нём
означает, что гамму делает кто-то, кроме формата swapchain.) Интерфейс ImGui в UNORM-swapchain
выглядит так, как задумано, — его цвета заданы уже в sRGB.

В ImGui тон-маппинг, цветокоррекция, sRGB-кодирование и дизеринг включаются независимо.
Там же — гистограмма (копируется с GPU в host-буфер для отображения, с задержкой на кадры в полёте),
min/max, целевое и адаптированное значение, экспозиция, GPU-время проходов.

### Шаг 3. 3D LUT

**Построение LUT** (`ColorLut.cpp`, при старте приложения):

1. Пространство RGB делится на 32×32×32 ячейки (каждая — 8 значений из 256 по каждому каналу).
2. Для каждого пикселя исходной картинки ячейка выбирается по его цвету.
3. В ячейке усредняются цвета соответствующих пикселей обработанной картинки.
4. Пустые ячейки берут цвет ближайшей заполненной (евклидово расстояние в пространстве ячеек).

Результат загружается в 3D-текстуру `R8G8B8A8_UNORM` 32³.

**Откуда картинки.** `luts/source.png` — два скриншота рендера (цветокоррекция выключена,
дизеринг выключен) и под ними «развёрнутая» единичная LUT: 32 плитки 32×32 (x = R, y = G,
плитка = B). Из-за неё заполняются **все** 32 768 ячеек, а скриншоты добавляют веса реально
встречающихся цветов. Скрипт: `luts/make_source.py`.

`graded.png` сделаны в **GIMP** (batch-режим, скрипт `luts/grade_gimp.scm`, только глобальные
поточечные операции: кривые, цветовой баланс по теням / полутонам / светам, тон/насыщенность):

* `film_warm` — мягкая S-кривая, чуть приподнятый чёрный, тёплые полутона и света, +15 % насыщенности
  (по умолчанию);
* `teal_orange` — бирюзовые тени, тёплые света, больше контраста;
* `cold_bleach` — «bleach bypass»: −45 % насыщенности, жёсткая кривая, холодный оттенок;
* `identity` — единичная LUT для проверки.

Любую пару можно заменить: открыть `source.png` в Photoshop / GIMP / Krita, сделать коррекцию
глобальными инструментами, сохранить `luts/<имя>/graded.png` — после перезапуска LUT появится в
списке.

**Применение.** Цвет после тон-маппинга и sRGB используется как координата `sampler3D` с линейной
фильтрацией. Тонкость: тексель k хранит среднее цветов из [k/32, (k+1)/32), центр этого
интервала (k + 0.5)/32 — ровно координата центра текселя. Поэтому координатой служит сам цвет,
без привычного `c · 31/32 + 0.5/32` (оно было бы правильным для LUT, где тексель k соответствует
цвету k/31). Есть слайдер силы LUT.

**Проверка.** Кадр приложения с LUT `film_warm` сравнивался с той же сценой, обработанной в GIMP:
средняя разница **0.87** уровня из 255 (99-й перцентиль — 3 уровня), а без LUT — 10.3. То есть
3D LUT 32³ с трилинейной интерполяцией почти точно воспроизводит цветокоррекцию редактора.

### Красота

* Дизеринг ±1/255 с треугольным распределением перед записью в 8 бит убирает полосы на гладком
  градиенте неба (выключается).
* Экспозиция по усечённому среднему не «пережигает» небо и не делает остров чёрным при взгляде
  на солнце, адаптация плавная.
* LUT по умолчанию — тёплый плёночный образ.

## Проверка

* Сборка с `-Wall -Wextra -Werror -pedantic` (gcc 13), clang-format.
* Validation layers с synchronization validation в режимах deferred / forward, shared / global,
  с переключением LUT — без сообщений. Validation нашёл две настоящие ошибки, обе исправлены:
  `vkCmdFillBuffer` относится к стадии COPY (а не CLEAR) — барьеры теперь по ALL_TRANSFER;
  и копия статистики в readback-буфер должна быть упорядочена с копией в тот же буфер двумя
  кадрами раньше (write-after-write между сабмитами).
* Etna не ставит барьеры для буферов, поэтому все переходы буфера состояния (очистка → min/max →
  гистограмма → экспозиция → пост-процесс / копия → следующий кадр) расставлены вручную.

## Параметры командной строки

```
--no-tonemap | --no-grading | --no-srgb | --no-dither | --lut NAME | --tonemap-op N (0 clamp, 1 Reinhard, 2 ACES, 3 Hable)
--global-atomics | --print-timings
--sun azimuth elevation | --coverage C | --no-clouds | --sky-size N
--forward | --naive | --no-decals | --debug-view N | --no-gui | --camera fx fy fz tx ty tz | --frames N
```

Шаг 1 в чистом виде: `tonemapping --no-tonemap --no-grading --no-srgb --no-dither`.
